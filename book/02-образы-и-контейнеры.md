## 2.0. Возврат в начало (сделай сам, без подсказок)

К концу главы 1 мы всё снесли — Docker на машине нет. Восстанови его сам, по памяти.
Задачи:

1. Подключи официальный репозиторий Docker (ключ + `sources.list.d`) и поставь
   `docker-ce`, `docker-ce-cli`, `containerd.io`, `docker-buildx-plugin`, `docker-compose-plugin`.
2. Разреши себе работать с Docker без `sudo` (группа `docker`) — так, чтобы это подействовало
   без перезагрузки.
3. Настрой ротацию логов Docker (`/etc/docker/daemon.json`, 10 МБ × 3 файла) и примени настройку.
4. Убедись, что `hello-world` запускается, а `docker compose version` и `docker buildx version`
   отвечают.

<details>
<summary>Показать команды</summary>

```bash
# 1. репозиторий + установка

sudo install -m 0755 -d /etc/apt/keyrings

sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 2. группа docker

# 3. ротация логов

{
  "log-driver": "json-file",
  "log-opts": { "max-size": "10m", "max-file": "3" },
  "live-restore": true

JSON

```

**Готов идти дальше, если:** `docker ps` работает **без** `sudo` и выводит пустую таблицу,
`docker info --format '{{.LoggingDriver}}'` отвечает `json-file`.

## 2.1. Зачем это в проде

Образ — это **неизменяемый** артефакт: собран один раз, дальше только копируется.
Контейнер — это **процесс**, запущенный из образа, плюс тонкий записываемый слой сверху.
Из одного образа можно поднять сто контейнеров, и они не будут знать друг о друге.

| | Образ (image) | Контейнер (container) |
|---|---|---|
| Что это | набор слоёв только для чтения + метаданные | процесс + записываемый слой + конфигурация |
| Где живёт | `/var/lib/docker/overlay2` + метаданные | процесс в своём namespace |
| Меняется? | нет (пересобирается) | да, но изменения умрут вместе с ним |
| Команда | `docker images`, `docker rmi` | `docker ps`, `docker rm` |
| Аналогия | класс | объект класса |

Три правила, которые в проде нарушают чаще всего:

1. **`latest` — не версия.** `docker run nginx` — это `nginx:latest`; завтра под этим тегом
   будет другой образ, и «вчера работало» перестанет работать. Пиннуй версию, а в идеале — digest.
2. **Контейнер — «домашний скот», а не «любимец».** Его не чинят руками, его убивают и
   поднимают заново из образа (или из манифеста в Kubernetes).
3. **Всё состояние — наружу.** Данные, которые нужны после перезапуска, живут в томе (глава 4),
   а не внутри контейнера.

## 2.3. Способ 1: самый простой запуск — `docker run` без всего

```bash
docker run hello-world
```

**Что произошло, по шагам (важно понять каждую строчку):**

1. Docker ищет образ `hello-world` локально — не находит.
2. Идёт в реестр (Docker Hub) и тянет `library/hello-world:latest` — без тега всегда `latest`.
3. Из образа создаётся контейнер, он запускается в **foreground** (терминал занят им).
4. Контейнер печатает текст и **завершается** с кодом `0`. Терминал освобождается.

**Проверка 1 — контейнер остался в истории, но уже не работает:**

```bash
docker ps -a --filter ancestor=hello-world
```

**Ожидаемо:** одна строка, статус `Exited (0) …` — контейнер существует, но не запущен.
Обрати внимание: имя ему дали случайное (`admiring_hopper` или подобное).

**Проверка 2 — образ появился локально:**

```bash
docker images hello-world
```

**Ожидаемо:** `hello-world  latest  <id>  2 minutes ago  17.1kB` — образ крошечный.

**Проверка 3 — какой код возврата был у контейнера:**

```bash
docker inspect -f '{{.State.Status}} exit={{.State.ExitCode}}' $(docker ps -aq --filter ancestor=hello-world | head -1)
```

**Ожидаемо:** `exited exit=0`.

## 2.4. Способ 2: detached-режим + публикация порта

```bash
docker run -d --name lab-web-8080 -p 8080:80 nginx:stable-alpine
```

**Что здесь каждое слово:**

| Флаг | Значение |
|---|---|
| `-d` | detached: Docker запускает контейнер и сразу возвращает терминал |
| `--name lab-web-8080` | фиксированное имя вместо случайного — чтобы не искать по ID |
| `-p 8080:80` | `<порт хоста>:<порт в контейнере>`: снаружи 8080, внутри nginx слушает 80 |
| `nginx:stable-alpine` | репозиторий `nginx`, тег `stable-alpine` (nginx на Alpine — маленький образ) |

**Проверка 1 — контейнер работает:**

```bash
docker ps
```

**Ожидаемо:** строка `lab-web-8080`, статус `Up …`, в колонке PORTS — `0.0.0.0:8080->80/tcp`.

**Проверка 2 — порт реально проброшен:**

```bash
docker port lab-web-8080
curl -sI http://localhost:8080 | head -3
```

**Ожидаемо:** `80/tcp -> 0.0.0.0:8080` и `HTTP/1.1 200 OK` от nginx. Если 200 нет — смотри
`docker logs lab-web-8080`.

**Проверка 3 — что внутри контейнера (а не на хосте) реально nginx:**

```bash
docker exec lab-web-8080 nginx -v
docker top lab-web-8080
```

**Ожидаемо:** `nginx version: nginx/1.x.y` и два процесса: `nginx: master process` (PID 1 внутри
контейнера) и worker.

**Проверка 4 — как Docker видит контейнер изнутри своей модели:**

```bash
docker inspect -f 'status={{.State.Status}} ip={{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}} pid={{.State.Pid}}' lab-web-8080
```

**Ожидаемо:** `status=running`, IP вида `172.17.0.2`, и PID — это PID процесса **на хосте**.

## 2.5. Способ 3: `pull` + `create` + `start` — три команды вместо одной

```bash
docker pull redis:8-alpine
```

**Что произошло:** образ скачан в локальный кэш и **ничего не запущено**. Это чистое
скачивание артефакта.

**Проверка 1 — образ на месте, и что у него внутри:**

```bash
docker images redis
docker image inspect redis:8-alpine --format 'id={{.Id}} size={{.Size}}B arch={{.Architecture}} os={{.Os}}'
```

**Проверка 2 — из каких слоёв он собран (это будущая тема главы 6):**

```bash
docker history redis:8-alpine | head -6
```

**Ожидаемо:** 6–8 слоёв, каждый — отдельная инструкция Dockerfile.

Теперь создаём контейнер, но **не запускаем**:

```bash
docker create --name lab-cache-6379 -p 6379:6379 redis:8-alpine
```

**Что произошло:** Docker создал контейнер (выделил записываемый слой, настроил сеть и порты)
и вернул длинный ID. Процесса внутри ещё нет.

**Проверка 3 — контейнер существует, но не работает:**

```bash
docker ps -a --filter name=lab-cache-6379
docker ps                # здесь его быть не должно!
```

**Ожидаемо:** в первом выводе статус `Created`, во втором — пусто.

Запускаем:

```bash
docker start lab-cache-6379
```

**Проверка 4 — теперь работает:**

```bash
docker ps --filter name=lab-cache-6379
docker exec lab-cache-6379 redis-cli ping
docker logs lab-cache-6379 | head -3
```

**Ожидаемо:** статус `Up …`, ответ `PONG`, в логах — строки старта Redis.

**Зачем вообще так делать:** `create` и `start` — две разные операции, и это удобно, когда
контейнер надо подготовить (задать лимиты, подключить к сети), а запустить позже; ровно так
же работает `docker run` внутри себя: `create` + `start` + `attach`.

## 2.6. Способ 4: интерактивный одноразовый контейнер (`-it --rm`)

```bash
docker run -it --rm --name lab-shell alpine:3 sh
```

**Что здесь:** `-i` — оставить STDIN открытым, `-t` — выделить псевдо-TTY (без них не будет
приглашения шелла), `--rm` — удалить контейнер сразу после выхода, `sh` — команда, которую
надо выполнить вместо стандартной.

Ты оказался **внутри** контейнера. Выполни там:

```sh
ps
cat /etc/os-release
hostname
ip a
ls /
exit
```

**Что наблюдать:**

- `ps` показывает **два** процесса, и `sh` — это **PID 1**. В контейнере нет systemd и нет
  обычного набора процессов; первый запущенный процесс и есть «init».
- `hostname` — это ID контейнера, а не имя твоей машины.
- `ip a` — свой сетевой интерфейс с адресом из подсети Docker (не твой `192.168.x.y`).
  (В Alpine `ip` — это `busybox`, поэтому сокращения вроде `ip -br a` там не работают.)
- `/etc/os-release` — `Alpine Linux` (а на хосте — Ubuntu). Одно ядро, разные «миры».

**Проверка после `exit` — контейнера больше нет:**

```bash
docker ps -a --filter name=lab-shell
docker images alpine
```

**Ожидаемо:** фильтр ничего не нашёл (спасибо `--rm`), а образ `alpine:3` на месте — образы
не удаляются вместе с контейнером.

## 2.7. Способ 5: переменные окружения, два порта и политика перезапуска

```bash
docker run -d \
  --name lab-mq-5672 \
  -p 5672:5672 \
  -p 15672:15672 \
  -e RABBITMQ_DEFAULT_USER=app \
  -e RABBITMQ_DEFAULT_PASS=app \
  --restart unless-stopped \
  rabbitmq:4-management-alpine
```

**Что здесь:** `-e` задаёт переменные окружения — именно так образы «официальных» сервисов
получают конфигурацию (никаких правок файлов внутри); два `-p`, потому что у RabbitMQ два
порта — 5672 (протокол AMQP) и 15672 (веб-панель управления); `--restart unless-stopped` —
политика: поднимать контейнер при падении процесса и при перезапуске демона, но не трогать,
если ты остановил его руками.

**Проверка 1 — контейнер работает, оба порта проброшены:**

```bash
docker ps --filter name=lab-mq-5672
docker port lab-mq-5672
```

**Ожидаемо:** статус `Up …`, `5672/tcp -> 0.0.0.0:5672`, `15672/tcp -> 0.0.0.0:15672`.

**Проверка 2 — RabbitMQ реально поднялся (а не просто «процесс жив»):**

```bash
docker exec lab-mq-5672 rabbitmq-diagnostics -q ping
docker exec lab-mq-5672 rabbitmqctl list_queues
```

**Ожидаемо:** `Ping succeeded` и пустая таблица очередей (мы ещё ничего не создавали).

**Проверка 3 — веб-панель отвечает и пускает с нашими кредами:**

```bash
curl -s -u app:app http://localhost:15672/api/overview | jq '{rabbitmq_version, cluster_name}'
```

**Ожидаемо:** `{"rabbitmq_version": "4.x.y", "cluster_name": "rabbit@…"}`.

**Проверка 4 — переменные окружения и политика перезапуска зафиксированы в контейнере:**

```bash
docker inspect -f '{{range .Config.Env}}{{println .}}{{end}}' lab-mq-5672 | grep RABBITMQ
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' lab-mq-5672
```

**Ожидаемо:** строки `RABBITMQ_DEFAULT_USER=app` и `RABBITMQ_DEFAULT_PASS=app`, политика
`unless-stopped`.

> **В проде:** пароли в `-e` попадают в `docker inspect` и в историю shell — это плохо.
> Правильно — секреты из файла (`--env-file`), из хранилища секретов (Vault, SOPS), а в
> Kubernetes — `Secret` (глава 12). Здесь `app/app` — учебный пароль, который никому не нужен.

## 2.10. Откат главы 2: убрать все пять контейнеров и образы

В главе 3 мы удалим контейнеры **пятью разными способами** — это будет отдельная тема.
Сейчас откат делаем самым быстрым способом, чтобы просто вернуться в чистое состояние.

```bash
# 1. работающие контейнеры — принудительно
docker rm -f lab-web-8080 lab-cache-6379 lab-mq-5672

# 2. остановленный (Exited) контейнер hello-world
docker rm $(docker ps -aq --filter ancestor=hello-world)

# 3. образы, которые мы скачали
docker rmi hello-world nginx:stable-alpine redis:8-alpine rabbitmq:4-management-alpine
```

**Проверка отката:**

```bash
docker ps -aq | wc -l
docker images -q | wc -l
docker system df
```

**Ожидаемо:** `0` контейнеров, `0` образов, в `docker system df` — нули по образам и
контейнерам. Если `docker rmi` ругается `image is being used by stopped container` — значит
какой-то контейнер ещё жив: `docker ps -a` и удали его.

**Итог:** Docker установлен и пуст, как сразу после главы 1.

## 2.11. Шпаргалка главы

```bash
# образы
docker images                                   # что скачано
docker pull nginx:stable-alpine                 # скачать
docker image inspect <образ> --format '{{.Id}} {{.Size}} {{.Architecture}}'
docker history <образ> | head                   # слои
docker rmi <образ>                              # удалить образ

# создать / запустить
docker run hello-world                          # foreground, образ без тега = :latest
docker run -d --name web -p 8080:80 nginx:stable-alpine
docker create --name cache -p 6379:6379 redis:8-alpine && docker start cache
docker run -it --rm --name shell alpine:3 sh
docker run -d --name mq -p 5672:5672 -p 15672:15672 -e K=V --restart unless-stopped rabbitmq:4-management-alpine

# смотреть, что получилось
docker ps                                       # только работающие
docker ps -a                                    # все, включая остановленные
docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'
docker port <имя>                               # куда проброшены порты
docker logs --tail 50 <имя>                     # логи
docker exec -it <имя> sh                        # зайти внутрь
docker top <имя>                                # процессы контейнера
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' <имя>
docker stats --no-stream                        # потребление ресурсов
docker system df                                # сколько всё это занимает

# удалить
docker rm <имя>                                 # остановленный
docker rm -f <имя>                              # работающий, принудительно
```

## 2.12. Типичные ошибки

| Симптом | Причина | Лечение |
|---|---|---|
| `docker: Error response from daemon: driver failed programming external connectivity … port is already allocated` | порт хоста занят | взять другой порт (`-p 8081:80`), найти занявший: `ss -ltnp \| grep 8080` |
| `Conflict. The container name "/lab-web-8080" is already in use` | имя занято старым контейнером | `docker rm -f lab-web-8080` или другое имя |
| `Unable to find image 'ngnix:latest' locally` + `pull access denied` | опечатка в имени образа | сверить имя на hub.docker.com |
| `no matching manifest for linux/amd64` | у образа нет варианта под твою архитектуру | выбрать другой тег/образ |
| контейнер сразу `Exited (1)` | процесс внутри упал | `docker logs <имя>` — там причина |
| `docker ps` пуст, хотя контейнер создан | контейнер не запущен | `docker ps -a`, затем `docker start` |
| `exec: "sh": executable file not found` | в образе нет `sh` (distroless/scratch) | `docker debug` или другой образ |
| после `-it` терминал «сломался» | контейнер убит без очистки tty | `reset` в терминале |
