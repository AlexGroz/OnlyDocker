## 3.1. Теория: контейнер — это процесс, у которого есть состояния

```text
            docker create            docker start
   [image] ─────────────► [created] ─────────────► [running] ◄──┐
                                ▲                     │  ▲      │ docker start
                                │                     │  └──────┘
                                │        docker stop  │
                                │        docker kill  ▼
                                └────────────────── [exited]
                                     (удалить: docker rm)
   running ── docker pause ──► paused ── docker unpause ──► running
```

| Состояние | Как получить | Что внутри |
|---|---|---|
| `created` | `docker create` | процесса нет, конфигурация есть |
| `running` | `docker start` / `docker run -d` | процесс работает |
| `paused` | `docker pause` | процесс заморожен (SIGSTOP), память занята |
| `exited` | процесс завершился или `docker stop` | процесса нет, записываемый слой жив |
| `dead` | сбой при удалении | «мусор», лечится `docker rm -f` |

### Коды выхода — это первое, что смотрят при инциденте

| Код | Значение | Типичная причина в проде |
|---|---|---|
| `0` | успех | нормальное завершение (batch-джоба) |
| `1` | ошибка приложения | исключение, отсутствует конфиг |
| `125` | ошибка самого Docker | неверные флаги `docker run` |
| `126` | команда не исполняемая | нет прав на файл |
| `127` | команда не найдена | опечатка в `CMD`/команде |
| `130` | 128+2, SIGINT | нажал Ctrl+C в `-it` |
| `137` | 128+9, SIGKILL | `docker kill`, **OOM-killer**, «не успел завершиться за 10 с» |
| `143` | 128+15, SIGTERM | корректно обработал `docker stop` |

### Проблема PID 1 (почему `docker stop` иногда занимает ровно 10 секунд)

`docker stop` отправляет процессу с PID 1 сигнал `SIGTERM`, ждёт **10 секунд** и только
потом бьёт `SIGKILL` — а это уже код `137` и потерянные транзакции. Хуже: для PID 1 ядро
**не применяет** стандартное поведение сигналов — если в программе нет обработчика `SIGTERM`,
она просто его проигнорирует. Поэтому в проде у приложения должен быть обработчик
корректного завершения (в .NET — `IHostApplicationLifetime`/`SIGTERM`-хендлер), а для чужих
бинарников ставят `--init` (крошечный init вроде `tini`, который перенаправляет сигналы).

### Политики перезапуска

| Политика | Когда перезапустит |
|---|---|
| `no` (по умолчанию) | никогда |
| `on-failure[:N]` | только при ненулевом коде выхода, не более N раз |
| `always` | всегда (и после перезапуска демона) |
| `unless-stopped` | всегда, кроме случая, когда ты остановил вручную |

## 3.2. Остановить, запустить, перезапустить

### Остановка

```bash
docker stop lab-web-8080
```

**Что произошло:** демон послал процессу `SIGTERM` («завершайся по-хорошему»), подождал до
10 секунд и завершил контейнер. nginx умеет корректно обрабатывать `SIGTERM`, поэтому
остановился сразу.

**Проверка 1 — контейнер остановлен, код выхода 0:**

```bash
docker ps -a --filter name=lab-web-8080 --format '{{.Names}} {{.Status}}'
docker inspect -f 'status={{.State.Status}} exit={{.State.ExitCode}}' lab-web-8080
```

**Ожидаемо:** статус `Exited (0) …` и `status=exited exit=0`.

**Проверка 2 — порт освободился (важно знать, когда «порт занят»):**

```bash
ss -ltn | grep ':8080' || echo "порт 8080 свободен"
curl -s -o /dev/null -w '%{http_code}\n' --max-time 2 http://localhost:8080 || echo "nginx не отвечает"
```

### Запуск

```bash
docker start lab-web-8080
```

**Проверка:**

```bash
docker ps --filter name=lab-web-8080
curl -s -o /dev/null -w 'nginx: %{http_code}\n' http://localhost:8080
```

**Ожидаемо:** `Up …` и `nginx: 200`.

### Перезапуск

```bash
docker restart lab-web-8080
```

**Проверка — время старта изменилось:**

```bash
docker inspect -f '{{.State.StartedAt}}' lab-web-8080; sleep 1; docker restart lab-web-8080 > /dev/null
docker inspect -f '{{.State.StartedAt}}' lab-web-8080
```

**Ожидаемо:** две разные метки времени.

## 3.3. Эксперимент: коды выхода и проблема PID 1

### Код выхода приложения

```bash
docker run --rm alpine:3 sh -c 'exit 42'; echo "код возврата: $?"
```

**Ожидаемо:** `код возврата: 42`. Docker честно возвращает код процесса — на этом строятся
CI-пайплайны (`docker run … && echo ok`).

### Контейнер, который не хочет останавливаться

```bash
docker run -d --name lab-signal alpine:3 sleep 300
docker kill -s SIGTERM lab-signal
```

**Проверка — а он всё ещё работает:**

```bash
docker ps --filter name=lab-signal --format '{{.Names}} {{.Status}}'
```

**Ожидаемо:** `lab-signal Up …`. Сигнал ушёл, но `sleep` — это **PID 1** контейнера, а для PID 1
ядро не применяет стандартное поведение сигналов. Программа без обработчика `SIGTERM`
его просто игнорирует. Это и есть «проблема PID 1».

Теперь то, что делает `docker stop` в такой ситуации:

```bash
time docker stop lab-signal
docker inspect -f 'exit={{.State.ExitCode}}' lab-signal
```

**Ожидаемо:** ~10 секунд ожидания и `exit=137` — то есть `128 + 9` (SIGKILL). Именно так в
проде теряются незакоммиченные транзакции и обрываются соединения.

### Лечение: `--init`

```bash
docker run -d --name lab-init --init alpine:3 sleep 300
docker kill -s SIGTERM lab-init
docker inspect -f 'status={{.State.Status}} exit={{.State.ExitCode}}' lab-init
```

**Ожидаемо:** контейнер остановился, `exit=143` (`128 + 15`) — сигнал был доставлен программе
крошечным init-процессом (`tini`), который стал PID 1.

Сравни две строки — `137` против `143`. В проде это разница между «заказ потерялся» и
«заказ корректно завершён».

**Проверка, что оба контейнера нам больше не нужны:**

```bash
docker ps -a --filter name=lab-signal --filter name=lab-init --format 'table {{.Names}}\t{{.Status}}'
```

## 3.4. Пауза, заморозка и разница с остановкой

```bash
docker pause lab-cache-6379
```

**Что произошло:** процесс получил `SIGSTOP` — он «заморожен», память занята, порт занят,
но обработки нет.

**Проверка 1 — статус `paused`:**

```bash
docker ps --filter name=lab-cache-6379 --format '{{.Names}} {{.Status}}'
docker inspect -f '{{.State.Status}}' lab-cache-6379
```

**Проверка 2 — контейнер не отвечает, но и не умер:**

```bash
timeout 3 docker exec lab-cache-6379 redis-cli ping; echo "код: $?"
```

**Ожидаемо:** команда не ответила за 3 секунды, код `124` (сработал `timeout`). Контейнер при
этом не остановлен — он именно заморожен.

```bash
docker unpause lab-cache-6379
```

**Проверка 3 — снова живой:**

```bash
docker exec lab-cache-6379 redis-cli ping
```

**Ожидаемо:** `PONG`.

> **В проде:** `pause` почти не используют. Ограничивать CPU/память (`--cpus`, `-m`) —
> правильнее; в Kubernetes это `resources.requests/limits` (глава 12).

## 3.5. Логи, события, изменения файловой системы

```bash
docker logs --tail 5 --since 10m lab-web-8080
```

**Проверка:** `docker logs --tail 1 lab-web-8080` — ровно одна строка (последняя).

```bash
docker events --since 10m --until "$(date -Is)" --filter container=lab-web-8080 | tail -5
```

**Что видим:** журнал событий демона: `start`, `restart`, `die`, `stop`. Это то, что нужно,
когда «контейнер сам перезапустился, а почему — непонятно».

```bash
docker diff lab-web-8080
```

**Что видим:** изменения записываемого слоя относительно образа: `C` — изменён, `A` — добавлен,
`D` — удалён. У nginx появятся `/var/cache/nginx`, `/var/run`.

```bash
docker rename lab-cache-6379 lab-cache && docker update --restart unless-stopped lab-cache
```

**Проверка:**

```bash
docker ps --filter name=lab-cache --format '{{.Names}} {{.Status}}'
docker inspect -f 'restart={{.HostConfig.RestartPolicy.Name}}' lab-cache
docker stats --no-stream --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}'
```

## 3.6. Пять способов удалить контейнер

Сначала подготовим материал: пять одинаковых контейнеров, два из них остановим.

```bash
for i in 1 2 3 4 5; do docker run -d --name lab-del-$i alpine:3 sleep 3600; done
docker stop lab-del-1 lab-del-2
```

**Проверка — три работают, два остановлены:**

```bash
docker ps -a --filter name=lab-del --format 'table {{.Names}}\t{{.Status}}'
```

### Способ 1: по имени (контейнер остановлен)

```bash
docker rm lab-del-1
```

**Почему так:** самый читаемый способ. Работает только с остановленным контейнером.

**Проверка:**

```bash
docker ps -a --filter name=lab-del-1 --format '{{.Names}}' || true
docker ps -a --filter name=lab-del --format '{{.Names}}' | wc -l
```

**Ожидаемо:** пустая строка и `4` — осталось четыре контейнера.

### Способ 2: по ID (сокращённому)

```bash
docker rm $(docker ps -aq --filter name=lab-del-2)
```

**Почему так:** имя можно изменить (`docker rename`), а ID — нет; в скриптах и CI чаще
используют ID, потому что он гарантированно уникален.

**Проверка:**

```bash
docker ps -a --filter name=lab-del --format 'table {{.Names}}\t{{.ID}}\t{{.Status}}'
```

**Ожидаемо:** три контейнера, `lab-del-2` исчез.

### Способ 3: принудительно, без остановки (`-f`)

```bash
docker rm -f lab-del-3
```

**Что произошло:** Docker отправил процессу `SIGKILL` и удалил контейнер одним действием.
Быстро и грязно: приложение не успело ничего сохранить.

**Проверка:**

```bash
docker ps -a --filter name=lab-del-3 --format '{{.Names}}' 
docker ps -a --filter name=lab-del --format '{{.Names}}' | wc -l
```

**Ожидаемо:** пусто и `2`.

### Способ 4: «по-хорошему» — сначала `stop` с таймаутом, потом `rm`

```bash
docker stop -t 20 lab-del-4 && docker rm lab-del-4
```

**Почему так:** `-t 20` даёт приложению 20 секунд на корректное завершение (по умолчанию 10).
Это правильный способ в проде: сначала «попрощаться», потом удалять.

**Проверка:**

```bash
docker ps -a --filter name=lab-del-4 --format '{{.Names}}'
echo "осталось: $(docker ps -a --filter name=lab-del --format '{{.Names}}')"
```

**Ожидаемо:** пусто и `осталось: lab-del-5`.

### Способ 5: массовая уборка — `prune`

```bash
docker stop lab-del-5
docker container prune -f
```

**Что произошло:** удалены **все** остановленные контейнеры — и `lab-del-5`, и всё, что
осталось остановленным от предыдущих шагов (`hello-world`, `lab-signal`, `lab-init`).

**Проверка:**

```bash
docker ps -a --format 'table {{.Names}}\t{{.Status}}'
```

**Ожидаемо:** остались только работающие: `lab-web-8080`, `lab-cache`, `lab-mq-5672`,
`lab-pg-5432` (если ты шёл по этой главе подряд — Postgres поднимется в главе 4,
поэтому его может не быть).

### Итог по пяти способам

| # | Способ | Команда | Когда применять |
|---|---|---|---|
| 1 | по имени | `docker rm <имя>` | руками, остановленный контейнер |
| 2 | по ID | `docker rm <id>` | скрипты, CI |
| 3 | принудительно | `docker rm -f <имя>` | завис, не реагирует |
| 4 | по-хорошему | `docker stop -t 20 <имя> && docker rm <имя>` | прод: дать приложению завершиться |
| 5 | массово | `docker container prune -f` | уборка всех остановленных |

## 3.7. Пять способов удалить образ

Образ нельзя удалить, пока его использует **работающий** контейнер — это защита, а не баг.

```bash
docker images
```

### Способ 1: по имени и тегу

```bash
docker rmi hello-world
```

**Проверка:** `docker images hello-world` → пусто (`docker images` список без него).

### Способ 2: по ID

```bash
docker rmi $(docker images -q alpine:3)
```

**Проверка:**

```bash
docker images --format 'table {{.Repository}}\t{{.Tag}}\t{{.ID}}\t{{.Size}}'
```

**Ожидаемо:** `alpine` исчез из списка.

### Способ 3: принудительно (`-f`) — и почему это ловушка

```bash
docker rmi -f rabbitmq:4-management-alpine
```

**Что произошло:** образ «отвязан» от имени, хотя контейнер `lab-mq-5672` продолжает работать
на нём. Docker разрешил это только из-за `-f`.

**Проверка 1 — образа с таким именем больше нет:**

```bash
docker images | grep -c rabbitmq || echo "образа rabbitmq больше нет"
```

**Проверка 2 — а контейнер жив и работает на безымянном образе:**

```bash
docker ps --filter name=lab-mq-5672 --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
```

**Ожидаемо:** в колонке `IMAGE` — `sha256:…`, а статус `Up`. Вот почему в проде сначала
удаляют контейнеры, а потом образы; иначе на диске остаётся «мусор», который не видно
в `docker images`.

### Способ 4: удалить всё неиспользуемое — `docker image prune -a -f`

```bash
docker image prune -a -f
```

**Что произошло:** удалены все образы, которые не используются ни одним контейнером.
Образы `nginx`, `redis` и `postgres` останутся — их держат работающие контейнеры.

**Проверка:**

```bash
docker images --format '{{.Repository}}:{{.Tag}}'
docker system df
```

**Ожидаемо:** только используемые образы, а `docker system df` показывает освободившееся место.

### Способ 5: полная уборка — `docker system prune -a --volumes -f`

**Внимание:** этот способ удаляет и **тома** — то есть данные базы. В лабе это цель,
в проде это катастрофа.

```bash
docker rm -f lab-web-8080 lab-cache lab-mq-5672 lab-pg-5432 2>/dev/null
docker system prune -a --volumes -f
```

**Проверка — система пуста:**

```bash
docker ps -a --format '{{.Names}}' | wc -l
docker images -q | wc -l
docker volume ls -q | wc -l
docker network ls --format '{{.Name}}' | grep -vE '^(bridge|host|none)$' | wc -l
docker system df
```

## 3.8. Откат главы 3

Тема этой главы — удаление, поэтому откат почти совпадает с темой: привести систему в
состояние «Docker установлен, внутри пусто».

```bash
docker rm -f $(docker ps -aq) 2>/dev/null
docker system prune -a --volumes -f
```

**Проверка отката — четыре нуля и пустая таблица:**

```bash
echo "контейнеры: $(docker ps -aq | wc -l)"
echo "образы:     $(docker images -q | wc -l)"
echo "тома:       $(docker volume ls -q | wc -l)"
echo "сети:       $(docker network ls --format '{{.Name}}' | grep -vE '^(bridge|host|none)$' | wc -l)"
docker system df
docker version --format 'Docker {{.Server.Version}} жив'
```

**Ожидаемо:** четыре нуля и сообщение о том, что демон жив.

Если нужно снять Docker совсем — это команды из раздела 1.9 главы 1.

## 3.9. Чек-лист самопроверки (глава 3)

| Вопрос | Ответ командой |
|---|---|
| В каком состоянии контейнер? | `docker ps -a`, `docker inspect -f '{{.State.Status}}'` |
| Какой код выхода и почему? | `docker inspect -f '{{.State.ExitCode}}'`, `docker events` |
| Сколько контейнер ждал SIGTERM? | `time docker stop <имя>` |
| Что значит код 137? | `128+9`, SIGKILL (или OOM) |
| Что значит код 143? | `128+15`, SIGTERM обработан |
| Как дать приложению больше времени? | `docker stop -t 30 <имя>` или `--stop-timeout` при запуске |
| Чем `pause` отличается от `stop`? | `docker pause` → `docker inspect -f '{{.State.Status}}'` |
| Кто «держит» образ и мешает его удалить? | `docker ps -a --filter ancestor=<образ>` |
| Что удаляет `system prune -a --volumes`? | `docker system df` до и после |

## 3.10. Шпаргалка главы

```bash
# жизненный цикл
docker stop <имя>            # SIGTERM → 10 с → SIGKILL
docker stop -t 30 <имя>      # дать 30 секунд
docker kill -s SIGTERM <имя> # только сигнал, без ожидания
docker kill <имя>            # SIGKILL
docker start <имя>
docker restart <имя>
docker pause <имя>; docker unpause <имя>
docker wait <имя>            # ждать завершения и вывести код
docker rename <старое> <новое>
docker update --restart unless-stopped <имя>

# диагностика
docker ps -a
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' <имя>
docker logs --tail 50 --since 15m <имя>
docker events --since 1h --until "$(date -Is)" --filter container=<имя>
docker diff <имя>
docker top <имя>
docker stats --no-stream

# удаление контейнеров (5 способов)
docker rm <имя>                          # по имени
docker rm <id>                           # по ID
docker rm -f <имя>                       # принудительно
docker stop -t 20 <имя> && docker rm <имя>
docker container prune -f                # все остановленные

# удаление образов (5 способов)
docker rmi <репозиторий:тег>
docker rmi <id>
docker rmi -f <репозиторий:тег>
docker image prune -a -f
docker system prune -a --volumes -f      # ВНИМАНИЕ: удаляет и тома
```

## 3.11. Типичные ошибки

| Симптом | Причина | Лечение |
|---|---|---|
| `You cannot remove a running container … Stop the container before attempting removal or force remove` | удаляешь работающий контейнер | `docker stop`, затем `docker rm` (или `-f`) |
| `docker stop` всегда занимает ровно 10 с | приложение — PID 1 без обработчика SIGTERM | `--init`, обработчик сигнала в коде, `-t` |
| код выхода `137` после `docker stop` | не успело завершиться → SIGKILL; либо OOM | `-t 60`, проверить `docker inspect .State.OOMKilled` |
| контейнер в статусе `Restarting` по кругу | падает при старте, а политика `always` | `docker logs`, `docker update --restart no`, разобраться |
| `docker rmi` → `image is being used by stopped container` | остановленный контейнер всё ещё держит образ | `docker ps -a`, удалить контейнер |
| `docker rmi -f` прошёл, а место не освободилось | образ остался как `<none>` (его держит контейнер) | удалить контейнеры, затем `docker image prune -a` |
| `docker exec` зависает | контейнер в `paused` | `docker unpause` |
| `No such container` | опечатка или контейнер удалён | `docker ps -a` |
| после `docker system prune --volumes` нет данных БД | том удалён «за компанию» | это необратимо; в проде `--volumes` не используют без бэкапа |

---

**Итог главы 3:** контейнер теперь для тебя — процесс с состояниями и кодом выхода, а не
«чёрный ящик». Ты умеешь его корректно останавливать (`SIGTERM` + таймаут), знаешь, откуда
берётся `137`, и владеешь пятью способами удаления контейнеров и образов.
