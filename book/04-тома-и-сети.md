## 4.1. Теория: почему данные умирают

У контейнера есть **записываемый слой** поверх образа. Всё, что процесс пишет в файловую
систему, попадает туда — и живёт ровно столько, сколько живёт контейнер. `docker rm` — данные
исчезли. Даже `docker stop` их не спасает от `docker rm` потом.

Поэтому состояние всегда выносят **наружу**, тремя способами монтирования:

| Тип | Флаг | Где данные | Кто управляет | Когда использовать |
|---|---|---|---|---|
| **named volume** | `-v lab-pgdata:/var/lib/postgresql` | `/var/lib/docker/volumes/lab-pgdata/_data` | Docker | данные БД, всё, что нужно пережить пересоздание контейнера; бэкапить через volume |
| **bind mount** | `-v /home/alexey/docker-lab/html:/usr/share/nginx/html:ro` | ровно там, где ты сказал | ты (хост) | конфиги, исходники, статические файлы при разработке |
| **tmpfs** | `--tmpfs /tmp` | в оперативной памяти | ядро | кэш, временные файлы, секреты, которые не должны попасть на диск |

Плюсы и минусы, которые спрашивают на собеседовании:

- **volume**: не зависит от структуры каталогов хоста, управляется Docker (`docker volume ls/rm/prune`),
  можно монтировать в несколько контейнеров, работает с драйверами (NFS, cloud-диски).
  Минус — «где это лежит?» неочевидно, и в бэкап-скрипт надо добавлять отдельную логику.
- **bind mount**: полный контроль и понятный путь; удобно для конфигов. Минус — привязка к
  пути хоста (на другой машине путь другой) и проблемы с правами: UID внутри контейнера не
  совпадает с UID на хосте, и приложение не может писать в каталог.
- **tmpfs**: быстро и не остаётся на диске. Минус — потеряется при остановке и занимает RAM.

### Важная деталь про образ `postgres`

В `postgres:18-alpine` каталог данных задан так: `PGDATA=/var/lib/postgresql/18/docker`,
а том объявлен как `VOLUME /var/lib/postgresql`. До 18-й версии было
`/var/lib/postgresql/data`. Если смонтировать «по старой памяти» не туда — Postgres
работает, но данные пишет мимо твоего тома, и они умирают вместе с контейнером.
Правило: **сначала смотри `docker image inspect`, потом монтируй**.

```bash
docker pull postgres:18-alpine     # образ нужен, чтобы заглянуть в него
docker image inspect postgres:18-alpine --format '{{json .Config.Env}}' | jq -r '.[]' | grep PGDATA
docker image inspect postgres:18-alpine --format '{{json .Config.Volumes}}'
```

**Ключи:** `docker pull` — скачать образ, ничего не запуская; `--format '{{json .Config.Env}}'` —
вывести переменные окружения образа **как JSON**; `jq -r '.[]'` — развернуть массив в строки;
`grep PGDATA` — оставить нужную переменную; `.Config.Volumes` — какие каталоги образ объявляет томами.

**Ожидаемо:** `PGDATA=/var/lib/postgresql/18/docker` и `{"/var/lib/postgresql":{}}` — то есть
монтировать надо `/var/lib/postgresql`, а не `/var/lib/postgresql/data`, как во всех статьях
для версий ≤ 17.

## 4.2. Теория: сети контейнеров

Сеть контейнера — это отдельный network namespace: свой интерфейс, свой IP, своя таблица
маршрутов, свои iptables-правила. Драйверы сети:

| Драйвер | Что даёт | Где применяется |
|---|---|---|
| `bridge` (по умолчанию) | виртуальный мост `docker0`, каждый контейнер получает IP из `172.17.0.0/16` | обычные контейнеры на одном хосте |
| **user-defined bridge** | свой мост + **встроенный DNS**: контейнеры видят друг друга **по имени** | так соединяют приложение и БД |
| `host` | контейнер использует сеть хоста напрямую, без NAT и без своего IP | максимальная производительность, но нет изоляции |
| `none` | сеть только `lo` | изоляция расчётов, «сеть не нужна» |
| `overlay` / `macvlan` | общение контейнеров на разных хостах | Docker Swarm, специфические задачи |

Главный практический факт: **в сети по умолчанию (`docker0`) DNS по именам не работает**,
там только IP (и устаревший `--link`). Стоит создать свою сеть — и `postgres`, `rabbitmq`,
`api` находят друг друга по именам контейнеров, а публиковать порты `-p` для внутреннего
общения больше не нужно.

## 4.3. Практика: данные умирают вместе с контейнером

Запускаем Postgres **без** тома вообще — «как делают новички».

```bash
docker run -d --name lab-pg-5432 \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=appdb \
  -p 5432:5432 postgres:18-alpine
```

**Ключи:** `-d` — в фоне; `--name` — имя контейнера; `-e ИМЯ=значение` — переменные окружения, из
которых образ postgres создаёт пользователя, пароль и базу (работают только при **первой**
инициализации тома); `-p 5432:5432` — опубликовать порт (`хост:контейнер`); `\` — перенос длинной
команды на следующую строку; `postgres:18-alpine` — образ с тегом (18.x на Alpine).

**Проверка 1 — база поднялась и готова принимать подключения:**

```bash
docker ps --filter name=lab-pg-5432 --format '{{.Names}} {{.Status}}'
docker logs lab-pg-5432 | tail -3
docker exec lab-pg-5432 pg_isready -U app
```

**Ключи:** `--filter name=` + `--format` — только этот контейнер и только два поля; `docker logs | tail -3` —
последние три строки лога (там postgres пишет, что готов принимать подключения);
`pg_isready -U app` — утилита из образа: проверяет, принимает ли сервер соединения под этим
пользователем (`-U` = user).

**Ожидаемо:** `Up …`, в логах `database system is ready to accept connections`, `… accepting connections`.

Создадим данные:

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c "create table t1(id int); insert into t1 values (1),(2);"
```

**Ключи:** `exec <контейнер> <команда…>` — выполнить внутри; `psql -U app` — клиент под пользователем
`app`, `-d appdb` — база `appdb`, `-c "..."` — выполнить переданный SQL и выйти (без `-c` открылся бы
интерактивный `psql`).

**Проверка 2 — данные на месте:**

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c "select count(*) from t1;"
```

**Ключи:** `psql -c "…"` — выполнить один SQL-запрос внутри контейнера и выйти;
`count(*)` — количество строк в таблице.

**Ожидаемо:** `2`.

Теперь «контейнер упал, поднимаем новый» — как в реальной жизни:

```bash
docker rm -f lab-pg-5432
docker run -d --name lab-pg-5432 \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=appdb \
  -p 5432:5432 postgres:18-alpine
sleep 5
docker exec lab-pg-5432 psql -U app -d appdb -c "select count(*) from t1;"
```

**Ключи:** `docker rm -f` — удалить работающий контейнер без остановки (для имитации «контейнер
пропал»); дальше тот же `run`; `sleep 5` — дать postgres инициализироваться, прежде чем стучаться
(«процесс запущен» ≠ «база готова»).

**Ожидаемо:** ошибка `ERROR: relation "t1" does not exist`. Данных нет.

**А теперь важный нюанс, который отличает «понимаю» от «слышал»:**

```bash
docker volume ls -f dangling=true
```

**Ключи:** `volume ls` — список томов; `-f dangling=true` (`--filter`) — только «потерянные» тома,
которые не подключены ни к одному контейнеру (обычно это анонимные тома от `VOLUME` в образе).

**Что видим:** один-два **анонимных** тома с длинными хешами. Почему? В образе `postgres`
объявлено `VOLUME /var/lib/postgresql`, поэтому Docker сам создал анонимный том и положил
данные туда. При `docker rm` (без `-v`) том **остался** — просто мы больше не знаем, какой
именно из анонимных томов принадлежал удалённому контейнеру. Данные физически есть, но
доступа к ним нет.

Вывод для прода: **анонимные тома — это потерянные данные**. Нужен явный, названный том.

## 4.4. Способ 1: named volume (именованный том)

```bash
docker volume create lab-pgdata
```

**Ключи:** `docker volume create <имя>` — создать **именованный** том (Docker выделит каталог
`/var/lib/docker/volumes/lab-pgdata/_data`). В отличие от анонимного, его можно найти по имени и
подключить к новому контейнеру.

**Проверка 1 — том создан и где он лежит:**

```bash
docker volume ls
docker volume inspect lab-pgdata --format '{{.Name}} {{.Driver}} {{.Mountpoint}}'
```

**Ключи:** `volume ls` — все тома; `volume inspect --format` — поля тома: `.Name` (имя),
`.Driver` (драйвер, обычно `local`), `.Mountpoint` (реальный путь на хосте).

**Ожидаемо:** `lab-pgdata local /var/lib/docker/volumes/lab-pgdata/_data`.

Теперь контейнер с этим томом и **правильным** путём для postgres 18:

```bash
docker rm -f lab-pg-5432 2>/dev/null
docker run -d --name lab-pg-5432 \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=appdb \
  -v lab-pgdata:/var/lib/postgresql \
  -p 5432:5432 postgres:18-alpine
```

**Ключи:** `-v <том>:<путь_в_контейнере>` — смонтировать именованный том; здесь
`lab-pgdata:/var/lib/postgresql` (именно `/var/lib/postgresql`, потому что в образе 18
`PGDATA=/var/lib/postgresql/18/docker`). `2>/dev/null` — не ругаться, если контейнера ещё нет.

**Проверка 2 — монтирование реально применилось:**

```bash
docker inspect lab-pg-5432 --format '{{range .Mounts}}{{.Type}} {{.Name}} -> {{.Destination}}{{println}}{{end}}'
```

**Ключи:** `{{range .Mounts}}…{{end}}` — перебрать все монтирования контейнера; `.Type` — тип
(`volume`/`bind`/`tmpfs`), `.Name` — имя тома (пусто у bind), `.Destination` — путь внутри
контейнера; `{{println …}}` — перевод строки после каждой записи.

**Ожидаемо:** `volume lab-pgdata -> /var/lib/postgresql`.

**Проверка 3 — данные лежат в томе, а не в контейнере:**

```bash
docker run --rm -v lab-pgdata:/v alpine:3 du -sh /v
docker run --rm -v lab-pgdata:/v alpine:3 ls /v
```

**Ключи:** `docker run --rm` — одноразовый контейнер «посмотреть и удалить»; `-v lab-pgdata:/v` —
подключить тот же том под коротким путём `/v`; `du -sh /v` — `-s` (только итог, без детализации),
`-h` (человекочитаемый размер); `ls /v` — что лежит внутри.

**Ожидаемо:** несколько десятков мегабайт и каталог `18` внутри — это и есть `PGDATA`.

Теперь повторим «аварию»:

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c "create table t1(id int); insert into t1 values (1),(2);"
docker exec lab-pg-5432 psql -U app -d appdb -c "select count(*) from t1;"
docker rm -f lab-pg-5432
docker run -d --name lab-pg-5432 \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=appdb \
  -v lab-pgdata:/var/lib/postgresql \
  -p 5432:5432 postgres:18-alpine
sleep 5
docker exec lab-pg-5432 psql -U app -d appdb -c "select count(*) from t1;"
```

**Ключи:** все ключи те же, что разобраны выше; единственный новый — `sleep 5` (подождать, пока
postgres поднимется на уже существующем томе).

**Ожидаемо:** `2`. Контейнер удалён и создан заново — **данные на месте**. Это и есть смысл тома.

**Бонус: бэкап базы без установки клиента на хост.**

```bash
docker exec lab-pg-5432 pg_dump -U app appdb > ~/docker-lab/reports/appdb.sql
wc -l < ~/docker-lab/reports/appdb.sql
```

**Ключи:** `pg_dump -U app appdb` — выгрузить базу `appdb` в SQL-текст (команда выполняется внутри
контейнера, клиент на хост ставить не нужно); `>` — перенаправить вывод **на хост** в файл;
`wc -l < файл` — посчитать строки, подав файл на вход.

## 4.5. Способ 2: bind mount (каталог с хоста внутрь контейнера)

```bash
mkdir -p ~/docker-lab/html
echo '<h1>bind mount: файл лежит на хосте</h1>' > ~/docker-lab/html/index.html
docker run -d --name lab-web-bind -p 8081:80 \
  -v ~/docker-lab/html:/usr/share/nginx/html:ro \
  nginx:stable-alpine
```

**Ключи:** `mkdir -p` — создать каталог вместе с родительскими, без ошибки при повторе;
`echo '…' > файл` — записать строку в файл (перезапись); `-v <путь_на_хосте>:<путь_в_контейнере>:ro` —
**bind mount**: путь с хоста виден внутри, `:ro` (`read-only`) запрещает контейнеру писать в него;
`-p 8081:80` — опубликовать порт; `-d` — в фоне.

**Проверка 1 — монтирование видно в конфигурации контейнера:**

```bash
docker inspect lab-web-bind --format '{{range .Mounts}}{{.Type}}: {{.Source}} -> {{.Destination}} rw={{.RW}}{{println}}{{end}}'
```

**Ключи:** `.Source` — путь **на хосте**, `.Destination` — путь в контейнере, `.RW` — `true`/`false`
(право записи; при `:ro` будет `false`), `.Type` — `bind`.

**Ожидаемо:** `bind: /home/alexey/docker-lab/html -> /usr/share/nginx/html rw=false`.

**Проверка 2 — контейнер отдаёт именно наш файл:**

```bash
curl -s http://localhost:8081 | head -2
```

**Ключи:** `curl -s` — без прогресса; `head -2` — первые две строки тела ответа (там наш `<h1>`).

**Ожидаемо:** `<h1>bind mount: файл лежит на хосте</h1>`.

**Проверка 3 — правка на хосте видна в контейнере сразу (без перезапуска):**

```bash
echo '<h1>я изменил файл на хосте</h1>' > ~/docker-lab/html/index.html
curl -s http://localhost:8081 | head -1
```

**Ключи:** `>` — перезаписать файл на хосте; `curl -s … | head -1` — сразу проверить, что контейнер
отдаёт новое содержимое (кэша нет: nginx читает файл с диска при каждом запросе).

**Ожидаемо:** новый текст. Именно так работают dev-окружения: код на хосте, рантайм в контейнере.

**Проверка 4 — `:ro` действительно защищает хост:**

```bash
docker exec lab-web-bind sh -c 'echo test > /usr/share/nginx/html/hack.txt' || echo "запись запрещена — так и надо"
```

**Ключи:** `sh -c '…'` — выполнить строку как команду оболочки (внутри нужен `>`);
`|| echo …` — печатать сообщение, если команда завершилась ошибкой (`Read-only file system`).

**Проверка 5 — главный подводный камень bind mount: владелец файлов**

```bash
docker run --rm -v ~/docker-lab/html:/data alpine:3 sh -c 'id -u; touch /data/from-container.txt'
ls -ln ~/docker-lab/html
```

**Ключи:** `id -u` — числовой UID пользователя внутри контейнера (`0` = root);
`touch <файл>` — создать пустой файл; `ls -ln` — `-n` (`--numeric-uid-gid`) показать владельца
числами, а не именем: так сразу видно, что файл принадлежит `0 0`.

**Ожидаемо:** внутри контейнера `id -u` = `0` (root), и новый файл на хосте принадлежит
`0 0`. Если приложение внутри контейнера работает не от root (например, uid 1000), оно
**не сможет** писать в каталог, принадлежащий root. Это причина половины вопросов
«в докере permission denied». Лечится `--user`, `chown` на хосте или (правильнее) отказом
от bind mount в пользу тома.

## 4.6. Способ 3: tmpfs (данные только в памяти)

```bash
docker run -d --name lab-tmpfs --tmpfs /tmp:rw,size=1m \
  alpine:3 sh -c 'while true; do date >> /tmp/log.txt; sleep 1; done'
```

**Ключи:** `--tmpfs /tmp:rw,size=1m` — смонтировать каталог в память с правом записи и лимитом 1 МБ;
`sh -c 'while true; do …; done'` — бесконечный цикл внутри контейнера; `>>` — дописывать в файл
(в отличие от `>`); цикл и `sleep 1` нужны, чтобы файл постоянно рос.

**Ключи:** `--tmpfs /tmp:rw,size=1m` — каталог `/tmp` внутри контейнера существует только
в RAM и не больше 1 МБ. На диск хоста не попадает ничего.

**Проверка 1 — файл пишется и растёт:**

```bash
sleep 3
docker exec lab-tmpfs wc -l /tmp/log.txt
docker exec lab-tmpfs df -h /tmp
```

**Ключи:** `sleep 3` — дать циклу записать несколько строк; `wc -l <файл>` внутри контейнера —
посчитать строки; `df -h /tmp` — тип и размер файловой системы, смонтированной в `/tmp`
(увидишь `tmpfs` и 1M).

**Ожидаемо:** 3–4 строки, и `df` показывает tmpfs размером 1 МБ.

**Проверка 2 — этого файла нет в записываемом слое контейнера:**

```bash
docker diff lab-tmpfs
```

**Ожидаемо:** в выводе нет `/tmp/log.txt` — tmpfs не является частью слоя контейнера.

**Проверка 3 — данные исчезли при перезапуске:**

```bash
docker restart lab-tmpfs && sleep 1 && docker exec lab-tmpfs wc -l /tmp/log.txt
```

**Ключи:** `restart` — перезапуск контейнера (tmpfs создаётся заново, содержимое теряется);
`&&` — выполнять по цепочке только при успехе; `sleep 1` — дать циклу записать первую строку;
`wc -l <файл>` — счётчик строк.

**Ожидаемо:** 1–2 строки, счёт пошёл заново — данные в памяти не переживают перезапуск.

> **В проде:** tmpfs используют для `read_only` файловых систем и секретов, которые не должны
> оказаться на диске. В Kubernetes аналог — `emptyDir: { medium: Memory }` (глава 13).

## 4.7. Все три способа одновременно — и сравнение

Теперь третий контейнер с **именованным томом**, чтобы все три способа работали в один момент.

```bash
docker volume create lab-webdata
docker run -d --name lab-web-vol -p 8083:80 -v lab-webdata:/usr/share/nginx/html nginx:stable-alpine
docker run --rm -v lab-webdata:/v alpine:3 sh -c 'echo "<h1>данные в named volume</h1>" > /v/index.html'
```

**Ключи:** `volume create` — создать именованный том; `-v lab-webdata:/usr/share/nginx/html` —
подключить его к nginx вместо каталога с хоста; `docker run --rm … sh -c 'echo … > /v/index.html'` —
одноразовый контейнер, который просто записывает файл в том (никакого `sudo` и прав root на хосте).

**Проверка 1 — все три контейнера живы и отдают каждый своё:**

```bash
docker ps --filter name=lab-web --format 'table {{.Names}}\t{{.Ports}}\t{{.Status}}'
echo "--- 8080 (без тома):"; curl -s http://localhost:8080 | head -1
echo "--- 8081 (bind):";     curl -s http://localhost:8081 | head -1
echo "--- 8083 (volume):";   curl -s http://localhost:8083 | head -1
```

**Ключи:** `--filter name=lab-web` — все контейнеры с `lab-web` в имени (подстрока); `--format` с
`.Ports` — колонка публикаций; `echo` перед `curl` — подпись, чтобы не путать, какой порт что вернул.

**Проверка 2 — данные тома переживают пересоздание контейнера:**

```bash
docker rm -f lab-web-vol
docker run -d --name lab-web-vol -p 8083:80 -v lab-webdata:/usr/share/nginx/html nginx:stable-alpine
curl -s http://localhost:8083 | head -1
```

**Ключи:** `rm -f` — удалить контейнер, не трогая том; `run -v <том>:…` — новый контейнер с тем же
томом; `curl | head -1` — проверить, что данные на месте.

**Ожидаемо:** `<h1>данные в named volume</h1>` — контейнер новый, данные старые.

**Проверка 3 — сводка: где что лежит**

```bash
for c in lab-web-8080 lab-web-bind lab-web-vol lab-tmpfs; do
  printf '%-14s ' "$c"
  docker inspect "$c" --format '{{range .Mounts}}{{.Type}}->{{.Destination}} {{end}}{{if not .Mounts}}нет монтирований{{end}}'
done
docker volume ls
```

**Ключи:** `printf '%-14s '` — имя контейнера в поле 14 символов, чтобы колонки не «плясали»;
`--format '…{{if not .Mounts}}…{{end}}'` — условие в шаблоне: если монтирований нет, печатать текст;
`docker volume ls` — все тома.

**Ожидаемо:** `lab-web-8080` — без монтирований (данные в слое контейнера!), `lab-web-bind` —
`bind->/usr/share/nginx/html`, `lab-web-vol` — `volume->/usr/share/nginx/html`, `lab-tmpfs` —
`tmpfs` (в `.Mounts` не отображается, смотри `.HostConfig.Tmpfs`).

| Способ | Переживает `docker rm` | Виден на хосте | Скорость | Типичное применение |
|---|---|---|---|---|
| слой контейнера | ❌ | ❌ | обычная | ничего важного |
| named volume | ✅ | через `/var/lib/docker/volumes` | обычная | БД, данные приложений |
| bind mount | ✅ | да, прямо в файловой системе | зависит от ФС | конфиги, dev-код |
| tmpfs | ❌ | ❌ (только RAM) | самая быстрая | кэш, секреты |

## 4.8. Сеть по умолчанию: IP есть, а DNS нет

```bash
docker network ls
docker network inspect bridge --format '{{range .IPAM.Config}}{{.Subnet}} шлюз {{.Gateway}}{{end}}'
```

**Ключи:** `network ls` — все сети (у любой установки есть `bridge`, `host`, `none`);
`network inspect --format` с `range .IPAM.Config` — конфигурация адресации: `.Subnet` (подсеть) и
`.Gateway` (шлюз для контейнеров).

**Проверка:** драйвер `bridge`, подсеть `172.17.0.0/16`, шлюз `172.17.0.1`.

Запустим два контейнера **без указания сети** (значит — сеть по умолчанию `bridge`):

```bash
docker run -d --name lab-default-a alpine:3 sleep 3600
docker run -d --name lab-default-b alpine:3 sleep 3600
```

**Ключи:** `-d` — в фоне; `--name` — имя; `sleep 3600` — «заглушка», чтобы контейнер жил час. Ключа
`--network` нет — значит контейнер попадёт в сеть по умолчанию `bridge`.

**Проверка 1 — у каждого свой IP в подсети Docker:**

```bash
for c in lab-default-a lab-default-b; do
  printf '%s ' "$c"; docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' "$c"
done
```

**Ключи:** цикл по именам; `printf '%s '` — печать имени **без** перевода строки, чтобы IP оказался
рядом; `--format '…{{.IPAddress}}…'` — адрес из настроек сети (в подсети `172.17.0.0/16`).

**Проверка 2 — по IP они друг друга видят:**

```bash
IP_B=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' lab-default-b)
docker exec lab-default-a ping -c 2 "$IP_B"
```

**Ключи:** `IP_B=$(…)` — сохранить вывод команды в переменную (кавычки в `"$IP_B"` обязательны);
`ping -c 2` — два пакета и остановка, иначе ping будет работать бесконечно; `docker exec` — выполнить
ping **изнутри** контейнера.

**Ожидаемо:** успешный ping.

**Проверка 3 — а по имени нет:**

```bash
docker exec lab-default-a ping -c 1 lab-default-b || echo "по имени не резолвится — это и есть проблема"
docker exec lab-default-a getent hosts lab-default-b || echo "DNS не знает такого имени"
```

**Ключи:** `ping -c 1 <имя>` — один пакет по **имени** (в сети по умолчанию DNS его не знает,
поэтому будет `bad address`); `getent hosts <имя>` — спросить системный резолвер; `|| echo` — печать
пояснения, если имя не разрешилось.

**Ожидаемо:** `bad address` или пусто. В сети по умолчанию встроенного DNS нет.

## 4.9. Своя сеть (user-defined bridge): имена работают

```bash
docker network create labnet
docker network inspect labnet --format 'подсеть={{range .IPAM.Config}}{{.Subnet}}{{end}} драйвер={{.Driver}}'
```

**Ключи:** `network create <имя>` — создать свою bridge-сеть (Docker выдаст следующий свободный
диапазон и включит встроенный DNS); `network inspect --format` — `.Subnet` из `.IPAM.Config` и
`.Driver` (тип сети).

**Проверка:** подсеть из диапазона `172.18.0.0/16` (Docker выдал следующий свободный),
драйвер `bridge`.

Запускаем два контейнера уже в своей сети:

```bash
docker run -d --network labnet --name lab-net-a alpine:3 sleep 3600
docker run -d --network labnet --name lab-net-b alpine:3 sleep 3600
```

**Ключи:** `--network <имя>` — подключить контейнер к **своей** сети (в ней работает DNS по именам);
остальные ключи — `-d`, `--name`, «заглушка» `sleep 3600` — уже знакомы.

**Проверка 1 — DNS по имени внутри сети:**

```bash
docker exec lab-net-a getent hosts lab-net-b
docker exec lab-net-a ping -c 2 lab-net-b
```

**Ключи:** `getent hosts <имя>` — разрешить имя через системный резолвер (в своей сети Docker
подставляет свой DNS); `ping -c 2` — два пакета и остановка.

**Ожидаемо:** строка с IP и успешный ping — **по имени**, без всяких IP.

**Проверка 2 — кто в сети состоит:**

```bash
docker network inspect labnet --format '{{range .Containers}}{{.Name}} {{.IPv4Address}}{{println}}{{end}}'
```

**Ключи:** `.Containers` — список участников сети; `range` перебирает их, `.Name` — имя контейнера,
`.IPv4Address` — адрес с маской, `{{println …}}` — перевод строки после каждой записи.

**Проверка 3 — контейнер можно подключить к двум сетям сразу:**

```bash
docker network connect labnet lab-default-a
docker inspect -f '{{range $name, $net := .NetworkSettings.Networks}}{{$name}}={{$net.IPAddress}} {{end}}' lab-default-a
docker exec lab-default-a ping -c 1 lab-net-b
```

**Ключи:** `network connect <сеть> <контейнер>` — подключить **уже запущенный** контейнер к ещё одной
сети (он окажется в двух сразу); `range $name, $net :=` — перебор словаря сетей: ключ — имя сети,
значение — её настройки; `ping -c 1` — один пакет по имени.

**Ожидаемо:** в выводе два имени сети (`bridge` и `labnet`) с разными IP, и ping по имени
`lab-net-b` работает — потому что контейнер теперь в сети с DNS.

```bash
docker network disconnect labnet lab-default-a
docker inspect -f '{{range $name, $net := .NetworkSettings.Networks}}{{$name}} {{end}}' lab-default-a
```

**Ключи:** `network disconnect <сеть> <контейнер>` — отключить от сети (контейнер продолжает
работать в оставшихся); тот же шаблон с `range` печатает уже один список сетей.

**Ожидаемо:** осталась только `bridge`.

> **В проде:** сервисы проекта кладут в одну сеть: `api`, `postgres`, `rabbitmq`. Тогда в
> конфигурации приложения пишут `Host=postgres` и `amqp://app:app@rabbitmq:5672/`, а порты
> `-p` публикуют только у `api`. База и брокер снаружи не видны вообще.

## 4.10. Ещё два драйвера: `host` и `none`

### `host` — сеть хоста напрямую

```bash
docker run -d --name lab-host --network host nginx:stable-alpine
```

**Ключи:** `--network host` — контейнер использует сеть **хоста**: своего IP и namespace у него нет,
поэтому `-p` не нужен и не работает — nginx сразу занимает порт 80 на хосте.

**Проверка 1 — nginx занял порт 80 хоста (никакого `-p` не нужно):**

```bash
ss -ltn | grep ':80 ' || echo "на 80 ничего нет"
curl -s -o /dev/null -w 'nginx на 80: %{http_code}\n' http://localhost:80
docker inspect lab-host --format 'network-mode={{.HostConfig.NetworkMode}} сетей={{len .NetworkSettings.Networks}}'
```

**Ключи:** `grep ':80 '` — пробел в конце, чтобы не поймать `:8080`; `curl -o /dev/null -w` — только
код ответа; `--format` с `.HostConfig.NetworkMode` (режим сети) и `len .NetworkSettings.Networks`
(сколько сетей у контейнера — при `host` будет `0`).

**Ожидаемо:** порт 80 слушается, nginx отвечает `200`, `network-mode=host`, а количество
сетей у контейнера — `0` (своего network namespace нет).

**Проверка 2 — и почему это опасно:**

```bash
docker port lab-host; echo "docker port молчит: при host-сети публиковать нечего"
```

Если порт 80 на хосте уже занят другим процессом — контейнер упадёт с `address already in use`.
Плюс никакой изоляции: контейнер видит все интерфейсы хоста.

```bash
docker rm -f lab-host    # освобождаем 80-й порт
```

**Ключи:** `rm -f` — удалить работающий контейнер без предварительного `stop` (иначе порт 80 остался
бы занятым); комментарий после команды — просто пояснение для читателя.

### `none` — сеть только для изоляции

```bash
docker run -d --name lab-none --network none alpine:3 sleep 3600
```

**Ключи:** `--network none` — контейнеру создаётся сетевой namespace только с интерфейсом `lo`:
наружу он не ходит и снаружи недоступен.

**Проверка:**

```bash
docker exec lab-none ip a
docker exec lab-none ping -c 1 -W 1 1.1.1.1 || echo "внешней сети нет — так и задумано"
```

**Ключи:** `ip a` — список интерфейсов и адресов (в `none`-сети будет только `lo`);
`ping -c 1 -W 1` — один пакет и ждать ответа не дольше 1 секунды (`-W` — таймаут в секундах),
чтобы команда не висела.

**Ожидаемо:** только интерфейс `lo`, ping не проходит.

## 4.11. Сводная проверка по сетям

```bash
docker network ls
docker ps --format 'table {{.Names}}\t{{.Networks}}'
for n in bridge labnet; do
  echo "== $n =="; docker network inspect "$n" --format '{{range .Containers}}  {{.Name}} {{.IPv4Address}}{{println}}{{end}}'
done
```

**Ключи:** `docker ps --format` с полем `.Networks` — в каких сетях состоит каждый контейнер;
цикл `for n in …` + `"$n"` (в кавычках, чтобы имя не развалилось) прогоняет `network inspect` по
обеим сетям; `echo "== $n =="` — заголовок перед выводом.

**Ожидаемо:** `lab-net-a` и `lab-net-b` — в `labnet`; `lab-default-a`/`lab-default-b` и
сервисные контейнеры — в `bridge`.

| Драйвер | Свой IP | DNS по имени | Изоляция | Публикация `-p` | Когда использовать |
|---|---|---|---|---|---|
| `bridge` (default) | да | **нет** | частичная | да | «просто запустить» |
| **user-defined bridge** | да | **да** | да | да | связка сервисов (наш случай) |
| `host` | нет (сеть хоста) | — | нет | не работает | максимальная производительность |
| `none` | только `lo` | — | полная | нет | изоляция, вычисления без сети |

## 4.15. Типичные ошибки

| Симптом | Причина | Лечение |
|---|---|---|
| `error while creating mount source path … no such file or directory` | каталога для bind mount нет на хосте | `mkdir -p` каталог **до** запуска |
| `permission denied` при записи в bind-каталог | uid в контейнере ≠ владелец каталога | `--user $(id -u):$(id -g)`, `chown`, или named volume |
| `chown: changing ownership of '/var/lib/postgresql/18/docker': Permission denied` | bind mount на каталог данных + postgres не root | не использовать bind для данных БД; владелец — uid 70 (alpine) |
| `FATAL: data directory has wrong ownership` | смонтирован каталог с чужими правами | тому дать управлять Docker (named volume) |
| после пересоздания контейнера нет данных | смонтирован не тот путь | сверить `PGDATA` из `docker image inspect` |
| `ping: bad address '<имя>'` | контейнеры в сети по умолчанию | создать свою сеть и поместить оба контейнера туда |
| `Error response from daemon: network <имя> not found` | сеть не создана или удалена | `docker network create <имя>` |
| `bind: address already in use` при `--network host` | порт занят на хосте | другой порт или обычная bridge-сеть |
| данные «пропали» после `docker volume prune` | том был неиспользуемый и его удалили | `docker volume prune` уносит данные; в проде — только с бэкапом |
| `tmpfs` не виден в `docker inspect .Mounts` | tmpfs не является mount-точкой `.Mounts` | смотреть `.HostConfig.Tmpfs` |
