## 5.1. Зачем это в проде

Настоящее приложение почти никогда не живёт в одиночку: ему нужна база, брокер, кэш, иногда
внешние API. В контейнерном мире каждый компонент — отдельный процесс со своим жизненным
циклом, а связывает их сеть и конфигурация.

| Правило | Как выглядит здесь | Почему так |
|---|---|---|
| **Один процесс — один контейнер** | `postgres`, `rabbitmq`, `api` — три контейнера | можно обновлять и масштабировать по отдельности |
| **Конфиг — из окружения** (12-factor) | `PG_CONN`, `AMQP_URI`, `QUEUE_NAME` | один и тот же образ работает в dev/stage/prod |
| **Состояние — в томе** | `lab-pgdata:/var/lib/postgresql` | контейнер можно убивать когда угодно |
| **Здоровье проверяется, а не предполагается** | `--health-cmd pg_isready` | «процесс жив» ≠ «сервис готов» |
| **Порядок запуска не гарантирован** | приложение умеет ждать БД и брокер | в кластере поды стартуют в любом порядке |

Почему приложение пока **на хосте**: чтобы увидеть, что «контейнеры — это просто процессы
в сети», и что подключение к контейнерной базе из хоста ничем не отличается от обычного —
нужен только опубликованный порт. В главе 6 мы упакуем его в образ, в главе 8 соберём всё
Compose-файлом, а в главе 11 увезём в Kubernetes.

> **В проде:** ровно так же, только вместо `-e POSTGRES_PASSWORD=app` — секреты из хранилища,
> вместо `-p 5432:5432` — ничего (база недоступна снаружи), а порядок запуска обеспечивает
> не человек, а платформа (health-пробы + ретраи).

**Что произошло:** создан минимальный веб-проект (`net8.0`, без HTTPS) и добавлены две

## 5.4. База и брокер — в контейнерах, в одной сети

```bash
docker network create labnet 2>/dev/null || echo "сеть labnet уже есть"
docker volume create lab-pgdata
```

**Ключи:** `network create` — своя сеть с DNS; `2>/dev/null` — скрыть ошибку, если сеть уже создана;
`|| echo …` — вместо ошибки напечатать понятный текст; `volume create` — именованный том для данных БД.

**Проверка:**

```bash
docker network ls --filter name=labnet
docker volume ls --filter name=lab-pgdata
```

**Ключи:** `network ls --filter name=` и `volume ls --filter name=` — показать только объекты с этим
именем (фильтр по подстроке, как и у `docker ps`).

Теперь PostgreSQL:

```bash
docker run -d --name lab-pg-5432 --network labnet \
  -v lab-pgdata:/var/lib/postgresql \
  -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app -e POSTGRES_DB=appdb \
  -p 5432:5432 \
  --health-cmd 'pg_isready -U app' --health-interval 5s --health-retries 10 \
  postgres:18-alpine
```

**Ключи:** `--network labnet` — в свою сеть; `-v <том>:<путь>` — данные в том; `-e` — креды и имя БД;
`-p 5432:5432` — порт для приложения на хосте; `--health-cmd '…'` — команда проверки здоровья
(выполняется внутри контейнера), `--health-interval 5s` — как часто, `--health-retries 10` — сколько
неудач до статуса `unhealthy`; `\` — перенос строки.

**Почему и `--network`, и `-p`:** сеть нужна, чтобы сетевое имя `lab-pg-5432` работало для
других контейнеров (пригодится в главе 6, когда приложение тоже уедет в контейнер), а `-p`
нужен **сейчас**, потому что приложение пока живёт на хосте и ходит на `localhost:5432`.

И RabbitMQ:

```bash
docker run -d --name lab-mq-5672 --network labnet \
  -e RABBITMQ_DEFAULT_USER=app -e RABBITMQ_DEFAULT_PASS=app \
  -p 5672:5672 -p 15672:15672 \
  --health-cmd 'rabbitmq-diagnostics -q ping' --health-interval 5s --health-retries 10 \
  rabbitmq:4-management-alpine
```

**Ключи:** те же, что у Postgres; отличие — два порта (`5672` — AMQP, `15672` — веб-панель) и своя
команда здоровья `rabbitmq-diagnostics -q ping` (`-q` — «тихо», только результат).

**Проверка 1 — оба контейнера стали healthy (RabbitMQ стартует ~10–15 секунд):**

```bash
sleep 20
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
docker inspect -f '{{.Name}} health={{.State.Health.Status}}' lab-pg-5432 lab-mq-5672
```

**Ключи:** `sleep 20` — дать сервисам стартовать и пройти первые healthcheck-и; `ps --format` с
`.Status` (в нём видно `(healthy)`) и `.Ports`; `inspect -f` с `.State.Health.Status` —
`starting`/`healthy`/`unhealthy`; `inspect` принимает **несколько** имён сразу.

**Ожидаемо:** оба `health=healthy`. Если `starting` — подожди ещё и проверь `docker logs`.

**Проверка 2 — каждый сервис отвечает по-своему:**

```bash
docker exec lab-pg-5432 pg_isready -U app
curl -s -u app:app http://localhost:15672/api/overview | jq -r '"rabbitmq " + .rabbitmq_version'
```

**Ключи:** `pg_isready -U app` — проверка готовности базы под пользователем `app`;
`curl -u app:app` — basic-auth к API; `jq -r '"rabbitmq " + .rabbitmq_version'` — собрать строку
(с `-r` — без кавычек JSON).

**Проверка 3 — DNS внутри сети: имена резолвятся:**

```bash
docker run --rm --network labnet alpine:3 getent hosts lab-pg-5432 lab-mq-5672
```

**Ключи:** `docker run --rm` — одноразовый контейнер-клиент; `--network labnet` — подключить его **в ту
же сеть**; `getent hosts <имена…>` — разрешить сразу два имени и напечатать IP.

**Ожидаемо:** две строки с IP. Это доказательство, что приложение **в контейнере** смогло бы
ходить в базу по имени `lab-pg-5432`.

**Проверка 4 — база реально принимает подключения и создала нашу БД:**

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c '\l' | head -8
```

**Ключи:** `psql -c '\l'` — метакоманда `\l` («list databases») выполняется и выходит;
`head -8` — первые восемь строк списка баз (там уже видно `appdb` и её владельца).

## 5.5. Запускаем приложение с конфигом из окружения

Открой **второй терминал** (первый пусть продолжает слушать RabbitMQ в логах) и запусти
приложение:

```bash
cd ~/docker-lab/api
export PG_CONN="Host=localhost;Port=5432;Username=app;Password=app;Database=appdb"
export AMQP_URI="amqp://app:app@localhost:5672/"
export QUEUE_NAME="orders"
export ASPNETCORE_URLS="http://localhost:8080"
dotnet run
```

**Ключи:** `export ИМЯ=значение` — положить переменную в окружение текущей оболочки, чтобы её
увидел запускаемый процесс (в кавычках — потому что внутри `;` и `:`); `ASPNETCORE_URLS` — адрес и
порт, которые слушает приложение; `dotnet run` — собрать и запустить проект, не занимая второй
терминал командами сборки.

**Что произошло:** приложение прочитало три переменные окружения и порт, подключилось к
Postgres, создало таблицу `orders` (если её не было) и начало слушать очередь.

**Проверка 1 — приложение ответило на запрос:**

```bash
curl -s http://localhost:8080/health | jq
```

**Ключи:** `curl -s` — только тело ответа, без прогресса; `jq` без аргументов — просто отформатировать
JSON (с отступами), так удобнее читать.

**Ожидаемо:**

```json
{ "status": "healthy", "db": "ok", "mq": "ok" }
```

**Проверка 2 — таблица действительно создана в контейнерной базе:**

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c '\d orders'
```

**Ключи:** `-c '\d orders'` — метакоманда `\d` («describe») печатает структуру таблицы: колонки,
типы, индексы, значения по умолчанию.

**Ожидаемо:** описание таблицы с колонками `id`, `item`, `qty`, `status`, `created_at`.

**Проверка 3 — очередь объявлена (durable):**

```bash
curl -s -u app:app http://localhost:15672/api/queues | jq -r '.[] | "очередь \(.name), сообщений: \(.messages)"'
```

**Ключи:** `-u app:app` — basic-auth; `jq -r '.[] | "…"'` — пройти по всем элементам массива (`.[]`)
и собрать строку: `\(.name)` — интерполяция поля внутрь строки, `-r` — вывод без кавычек.

**Ожидаемо:** `очередь orders, сообщений: 0`.

> **В проде:** эти переменные не «экспортируют руками», а передают через systemd-юнит,
> `docker run -e/--env-file`, Kubernetes `ConfigMap`/`Secret` (глава 12) или Vault.
> Код при этом не меняется вообще — в этом и смысл 12-factor.

## 5.6. Сквозной сценарий: заказ проходит через все три компонента

Создаём заказ:

```bash
curl -s -X POST http://localhost:8080/orders \
  -H 'Content-Type: application/json' \
  -d '{"item":"book","qty":2}' | jq
```

**Ключи:** `-X POST` — HTTP-метод (`-X` = `--request`); `-H 'Content-Type: application/json'` —
заголовок, без него сервер не разберёт тело; `-d '<json>'` (`--data`) — тело запроса; `\` —
перенос строки; `| jq` — красиво напечатать ответ.

**Ожидаемо:** `{ "id": 1, "status": "new" }`.

Через пару секунд смотрим результат в трёх местах:

```bash
sleep 2
echo "== API:";        curl -s http://localhost:8080/orders | jq
echo "== БД:";         docker exec lab-pg-5432 psql -U app -d appdb -c 'select id,item,qty,status from orders order by id;'
echo "== очередь:";    curl -s -u app:app http://localhost:15672/api/queues | jq -r '.[] | "сообщений: \(.messages)"'
```

**Ключи:** `sleep 2` — дать потребителю обработать сообщение; `echo "== …"` — подписи секций
(`;` — просто разделитель команд); `psql -c 'select …'` — запрос и выход; `jq -r '.[] | …'` — по
строке на каждую очередь.

**Ожидаемо:**

- в API и в БД у заказа `status = processed`;
- в очереди `сообщений: 0` — сообщение обработано и подтверждено (`ack`).

Это и есть полный путь: **HTTP → PostgreSQL → RabbitMQ → потребитель → PostgreSQL**.
Ровно та же схема будет работать, когда все три части окажутся в контейнерах, а потом в
Kubernetes.

Добавим ещё пару заказов и убедимся, что счёт идёт:

```bash
for i in 1 2 3; do curl -s -X POST http://localhost:8080/orders -H 'Content-Type: application/json' -d "{\"item\":\"item-$i\",\"qty\":$i}" > /dev/null; done
curl -s http://localhost:8080/orders | jq 'length'
docker exec lab-pg-5432 psql -U app -d appdb -c "select status, count(*) from orders group by status;"
```

**Ключи:** цикл `for i in 1 2 3` запускает `curl` трижды; внутри `-d "{\"item\":\"item-$i\"…}"` —
кавычки экранированы (`\"`), потому что внешние кавычки двойные, а `$i` подставляется оболочкой;
`> /dev/null` — тело ответа не нужно; `jq 'length'` — длина массива, то есть число заказов;
`count(*) … group by status` — сколько заказов в каждом статусе.

**Ожидаемо:** `4` заказа в API и все `processed` — теперь очередь пуста, а данные в базе есть.

## 5.7. А теперь сломаем брокер (проверка на устойчивость)

```bash
docker stop lab-mq-5672

curl -s -o /dev/null -w 'health: %{http_code}\n' http://localhost:8080/health
curl -s http://localhost:8080/health | jq
```

**Ключи:** `docker stop` — корректно остановить контейнер (SIGTERM, затем SIGKILL); `sleep 6` — дать
приложению заметить обрыв; `curl -o /dev/null -w '%{http_code}'` — только код ответа (ждём `503`);
второй `curl | jq` — тело ответа, чтобы увидеть причину.

**Ожидаемо:** `503` и `"mq": "fail: нет соединения с RabbitMQ"`. Приложение не упало — оно
честно сообщает, что зависимость недоступна.

```bash
curl -s -o /dev/null -w 'POST /orders: %{http_code}\n' -X POST http://localhost:8080/orders \
  -H 'Content-Type: application/json' -d '{"item":"lost","qty":1}'
docker exec lab-pg-5432 psql -U app -d appdb -c "select id,item,status from orders order by id desc limit 2;"
```

**Ключи:** `-w '%{http_code}'` печатает код ответа (`500`), а `-o /dev/null` выбрасывает тело;
`order by id desc limit 2` — две последние строки: видно, что заказ записан, хотя сообщение не ушло.

**Ожидаемо:** `500`, но заказ **уже записан** в БД со статусом `new` — сообщение в очередь
уйти не смогло. Это классическая проблема «dual write».

> **В проде:** такие потери лечат паттерном **Transactional Outbox** (писать событие в ту же
> БД-транзакцию, а публиковать отдельным воркером) или saga-подходом. Для нашей книги важен
> сам факт: «два хранилища — два источника правды», и об этом думают заранее.

Возвращаем брокер и смотрим, как приложение само переподключилось:

```bash
docker start lab-mq-5672
sleep 10
curl -s http://localhost:8080/health | jq
curl -s -u app:app http://localhost:15672/api/queues | jq -r '.[] | "очередь \(.name), сообщений: \(.messages)"'
```

**Ключи:** `docker start` — поднять тот же контейнер (данные брокера на месте);
`sleep 10` — время на переподключение потребителя (в коде заложена пауза 5 секунд между попытками);
дальше — проверка здоровья и очередей.

**Ожидаемо:** снова `healthy`, `mq: ok`, очередь `orders` на месте (она `durable`, поэтому
пережила перезапуск брокера).

Последний штрих — «добить» зависший заказ: он так и останется в статусе `new`, потому что
сообщение потерялось. Убедимся:

```bash
docker exec lab-pg-5432 psql -U app -d appdb -c "select status, count(*) from orders group by status;"
```

**Ключи:** `psql -c "…"` — выполнить один запрос; `count(*)` считает строки, `group by status` —
отдельно по каждому статусу. Ожидаем: одна строка `new` (та, чьё сообщение потерялось) и остальные
`processed`.

## 5.11. Типичные ошибки

| Симптом | Причина | Лечение |
|---|---|---|
| `Npgsql.NpgsqlException: Connection refused (localhost:5432)` | контейнер БД не готов / не опубликован порт | `docker ps`, `docker inspect .State.Health.Status` |
| `password authentication failed for user "app"` | другой пароль у уже существующего тома | `POSTGRES_PASSWORD` применяется только при **первой** инициализации тома |
| `database "appdb" does not exist` | том создан с другим `POSTGRES_DB` | удалить том и поднять заново |
| `RabbitMQ.Client.Exceptions.BrokerUnreachableException` | брокер ещё стартует | подождать healthcheck, приложение само переподключится |
| `404` на `/orders` при `POST` | неверный путь или метод | `curl -i`, смотреть маршруты в `Program.cs` |

## Приложение А. Полный код приложения (`Program.cs`)

Файл целиком — как в `book/assets/app/Program.cs`. Он компилируется на .NET SDK 8.0 с
`Npgsql 8.0.6` и `RabbitMQ.Client 7.1.2`.

```csharp
// Минимальное API: заказ → PostgreSQL + RabbitMQ.
// Глава 5 книги: приложение запускается на ХОСТЕ, Postgres и RabbitMQ — в контейнерах.
// Всё, что «настраивается», приходит из переменных окружения (12-factor).
using System.Text.Json;
using Npgsql;
using RabbitMQ.Client;
using RabbitMQ.Client.Events;

var builder = WebApplication.CreateBuilder(args);

static string Env(string name, string fallback) =>
    Environment.GetEnvironmentVariable(name) is { Length: > 0 } v ? v : fallback;

string pgConn    = Env("PG_CONN", "Host=localhost;Port=5432;Username=app;Password=app;Database=appdb");
string amqpUri   = Env("AMQP_URI", "amqp://app:app@localhost:5672/");
string queueName = Env("QUEUE_NAME", "orders");

builder.Services.AddSingleton(_ => NpgsqlDataSource.Create(pgConn));
builder.Services.AddSingleton(new RabbitOptions(new Uri(amqpUri), queueName));
builder.Services.AddSingleton<OrdersConsumer>();
builder.Services.AddHostedService(sp => sp.GetRequiredService<OrdersConsumer>());

var app = builder.Build();

// --- схема БД создаётся на старте: в лабе удобно, в проде этим занимаются миграции ---
await using (var conn = await app.Services.GetRequiredService<NpgsqlDataSource>().OpenConnectionAsync())
await using (var cmd = new NpgsqlCommand(
    "create table if not exists orders (" +
    "id bigserial primary key, " +
    "item text not null, " +
    "qty int not null, " +
    "status text not null default 'new', " +
    "created_at timestamptz not null default now())", conn))
{
    await cmd.ExecuteNonQueryAsync();
}

// 1. Живость: приложение + БД + брокер
app.MapGet("/health", async (NpgsqlDataSource ds, OrdersConsumer consumer) =>
{
    string dbState = "ok", mqState = consumer.IsConnected ? "ok" : "fail: нет соединения с RabbitMQ";
    try
    {
        await using var conn = await ds.OpenConnectionAsync();
        await using var cmd = new NpgsqlCommand("select 1", conn);
        await cmd.ExecuteScalarAsync();
    }
    catch (Exception e) { dbState = "fail: " + e.Message; }

    bool healthy = dbState == "ok" && mqState == "ok";
    return Results.Json(new { status = healthy ? "healthy" : "degraded", db = dbState, mq = mqState },
                        statusCode: healthy ? 200 : 503);
});

// 2. Создать заказ: пишем в PostgreSQL и публикуем сообщение в очередь
app.MapPost("/orders", async (OrderRequest req, NpgsqlDataSource ds, RabbitOptions opts) =>
{
    long id;
    await using (var conn = await ds.OpenConnectionAsync())
    await using (var cmd = new NpgsqlCommand(
        "insert into orders (item, qty) values (@item, @qty) returning id", conn))
    {
        cmd.Parameters.AddWithValue("item", req.Item);
        cmd.Parameters.AddWithValue("qty", req.Qty);
        id = (long)(await cmd.ExecuteScalarAsync())!;
    }

    var (connection, channel) = await RabbitChannel.OpenAsync(opts);
    await using (connection)
    await using (channel)
    {
        await channel.BasicPublishAsync(exchange: string.Empty, routingKey: opts.Queue,
                                        body: JsonSerializer.SerializeToUtf8Bytes(new { id, req.Item }));
    }

    return Results.Created($"/orders/{id}", new { id, status = "new" });
});

// 3. Прочитать последние заказы
app.MapGet("/orders", async (NpgsqlDataSource ds) =>
{
    var rows = new List<object>();
    await using var conn = await ds.OpenConnectionAsync();
    await using var cmd = new NpgsqlCommand(
        "select id, item, qty, status from orders order by id desc limit 20", conn);
    await using var rdr = await cmd.ExecuteReaderAsync();
    while (await rdr.ReadAsync())
        rows.Add(new { id = rdr.GetInt64(0), item = rdr.GetString(1), qty = rdr.GetInt32(2), status = rdr.GetString(3) });
    return Results.Ok(rows);
});

app.Run();

// ---------------------------------------------------------------------------

record OrderRequest(string Item, int Qty);
record RabbitOptions(Uri Uri, string Queue);

// Соединение и канал поднимаются на каждый запрос: в лабе просто,
// в проде держат один долгоживущий канал или клиент с пулом.
static class RabbitChannel
{
    public static async Task<(IConnection Connection, IChannel Channel)> OpenAsync(RabbitOptions opts)
    {
        var factory = new ConnectionFactory { Uri = opts.Uri };
        var connection = await factory.CreateConnectionAsync();
        var channel = await connection.CreateChannelAsync();
        await channel.QueueDeclareAsync(queue: opts.Queue, durable: true, exclusive: false, autoDelete: false);
        return (connection, channel);
    }
}

// Фоновый потребитель: читает очередь и переводит заказ в статус 'processed'
sealed class OrdersConsumer(NpgsqlDataSource ds, RabbitOptions opts, ILogger<OrdersConsumer> log)
    : BackgroundService
{
    private IConnection? _connection;
    public bool IsConnected => _connection is { IsOpen: true };

    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        var factory = new ConnectionFactory { Uri = opts.Uri };
        while (!ct.IsCancellationRequested)
        {
            try
            {
                await ConnectAndConsumeAsync(factory, ct);
            }
            catch (Exception e)
            {
                log.LogWarning("RabbitMQ недоступен ({Message}), повтор через 5 секунд", e.Message);
                await Task.Delay(TimeSpan.FromSeconds(5), ct);
            }
        }
    }

    private async Task ConnectAndConsumeAsync(ConnectionFactory factory, CancellationToken ct)
    {
        if (_connection is not null) await _connection.DisposeAsync();

        _connection = await factory.CreateConnectionAsync(ct);
        var channel = await _connection.CreateChannelAsync(cancellationToken: ct);
        await channel.QueueDeclareAsync(opts.Queue, durable: true, exclusive: false,
                                        autoDelete: false, cancellationToken: ct);

        var consumer = new AsyncEventingBasicConsumer(channel);
        consumer.ReceivedAsync += async (_, ea) =>
        {
            long id = JsonDocument.Parse(ea.Body.ToArray()).RootElement.GetProperty("id").GetInt64();
            await using (var conn = await ds.OpenConnectionAsync(ct))
            await using (var cmd = new NpgsqlCommand("update orders set status = 'processed' where id = @id", conn))
            {
                cmd.Parameters.AddWithValue("id", id);
                await cmd.ExecuteNonQueryAsync(ct);
            }
            await channel.BasicAckAsync(ea.DeliveryTag, multiple: false, cancellationToken: ct);
            log.LogInformation("Заказ {Id} обработан", id);
        };

        await channel.BasicConsumeAsync(opts.Queue, autoAck: false, consumer: consumer, cancellationToken: ct);
        log.LogInformation("Слушаю очередь {Queue}", opts.Queue);

        // ждём, пока соединение не закроется (упал брокер, перезапуск контейнера и т.п.),
        // и уходим на переподключение во внешнем цикле
        var closed = new TaskCompletionSource();
        _connection.ConnectionShutdownAsync += (_, args) =>
        {
            log.LogWarning("Соединение с RabbitMQ закрыто: {Reason}", args.ReplyText);
            closed.TrySetResult();
            return Task.CompletedTask;
        };
        await closed.Task;
    }
}
```

**Что здесь важно для дальнейших глав:**

- `NpgsqlDataSource` — пул соединений, создаётся один раз;
- потребитель — `BackgroundService`, то есть живёт столько же, сколько приложение;
- приложение **не падает**, если RabbitMQ недоступен: оно предупреждает в лог и повторяет
  попытку каждые 5 секунд — именно этого ждут от контейнера в кластере;
- вся конфигурация — из окружения. В главе 6 мы упакуем это в образ, и тот же самый код
  поедет в контейнер без единой правки.
